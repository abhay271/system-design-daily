Design a file sync service (Dropbox-style)

You save a file on your laptop and it shows up on your phone. The interview asks how to move big files over shaky wifi without starting over, and how the other devices find out something changed.

Features Qualities Entities API Design Deep dives Tips
Legend 6 terms used below
Chunk
A fixed-size piece of a file, about 4 MB.
Hash
A short fingerprint computed from some bytes. The same bytes always give the same fingerprint, and different bytes almost never do.
Blob storage
Cheap storage for huge numbers of big files by key, such as Amazon S3.
Pre-signed URL
A link our server makes that allows one upload or download of one object for a short time.
API gateway
The single front door of a system. It sends each request to the right service.
Long polling
The server holds a request open until there is news or a timeout.

Functional requirements

  • Upload a file, or a new version of one.
  • Download a file.
  • See changes made on your other devices.

Out of scope: sharing, version history screens, folder watching.

Non-functional requirements

  • Reliable uploads. Wifi drops, and a hiccup must not restart a 2 GB upload.
  • Quick sync. Changes should show on other devices within seconds.
  • Never lose or overwrite work. Two devices may edit one file, and saved files must survive failures.

Core entities

  • File: its path, owner, current version, and the ordered list of its chunk hashes.
  • Chunk: one piece of bytes, stored under its hash.
  • Change: "this file is now version N", numbered in order.

API design

Starts an upload. The client splits the file into chunks and sends each hash. It gets links only for chunks not stored yet. Over 5 GB gets 413.

High-level design

Assume 10 million users making 5 changes a day: 50 million a day, about 600 a second. One database handles that, because only a small record per change reaches our servers. The app servers are identical, keep no data, and sit behind a load balancer.

1. Upload

The client sends the chunk hashes. The server asks the blob storage which chunks it already holds and returns a pre-signed URL for each missing one. The client uploads them straight to blob storage, then calls commit.

Commit checks the chunks exist, then does one guarded update that only succeeds if the file is still at base_version. Otherwise the client gets 409 and keeps its copy as a "conflicted copy". File IDs are random UUIDs, and change numbers come from a database sequence.

2. Download

The client gets the chunk list with a signed link each, fetches them in parallel and joins them. No CDN, since files are private.

3. Sync

Each device remembers a cursor, the last change number it has seen, and asks for changes after it. A delete is a row marked deleted, so devices hear about it too.

Why

Why not send files through our servers? They would carry every gigabyte. A signed link lets the client talk to storage directly while we still control who uploads.

Deep dives

How do we make big uploads reliable?

One dropped request must not throw away hours of upload.

  1. One request per file. Simple, but any drop restarts the whole file.
  2. Chunks through our servers. Resumable, but they carry every byte.
  3. Chunks straight to blob storage.Pick Resumable, and our servers stay small.

Each chunk has its own link, and a failed chunk is retried alone. After a crash the client repeats POST /files and only the chunks still missing are sent. Storage keeps several copies of each chunk, which covers durability.

How do other devices hear about a change fast?

Devices need news in seconds, yet most of the time there is none.

  1. Poll every 5 seconds. Simple, but 1 million online devices send 200,000 mostly empty requests a second.
  2. Long polling.Pick Few requests, and news arrives within seconds.
  3. WebSocket. Instant, but millions of connections stay open for rare news.

With long polling, a device sends GET /changes and waits up to 30 seconds. The Sync service re-checks the index every couple of seconds and answers once a change appears.

Final design

The dives added chunked uploads and a waiting changes feed. The Upload service writes records and checks blob storage, while the Sync service holds many waiting requests. Those loads differ, so each scales on its own. An API gateway routes by path.

If the database primary dies, the replica takes over; meanwhile uploads get 503 and retry, and stored chunks are safe. No cache or queue yet: reads are one indexed lookup and nothing slow follows a commit. File records come from the primary; the changes feed may lag a few seconds.

What you could add next

  • A pub/sub channel that nudges waiting devices, replacing re-checks.
  • Content-defined chunk boundaries, so an insert doesn't change every chunk.
  • A CDN for shared files.

Interview tips

Two devices edit the same file?
First commit wins. The second gets 409 and saves a copy.
Why hash the chunks?
Same hash, same bytes, so we skip chunks already stored.
A phone was offline for a week?
It asks for changes after its cursor, page by page.

Common mistakes

  • Re-uploading the whole file for a small edit.
  • Streaming file bytes through the app servers instead of using signed links.
Interview tip

Say early: small records through our servers, big bytes straight to storage.

Confidence note

The user counts, 4 MB chunks, 5 GB limit and 15-minute links are assumptions. WebSockets are also a valid answer.

Design a key-value store

A key-value store is a giant labelled shelf: you save a value under a name and later ask for it by that name. The interview asks how to spread it over many machines without losing data when one breaks.

Features Qualities Entities API Design Deep dives Tips
Legend 5 terms used below
Tombstone
A "this key was deleted" marker saved in place of the value. It stops an old copy from bringing the key back.
Hash ring
A circle that machines and keys are both placed on, using a hash function (a rule that turns any text into a number). A key belongs to the first machine clockwise from it.
Replica
A copy of the data kept on another machine, so one machine dying loses nothing.
Quorum
A majority. A write counts once most copies confirm it, and a read asks most copies.
API gateway
The single front door of a system. It sends each request to the right service.

Functional requirements

  • Save a value under a key.
  • Get the value for a key.
  • Delete a key.

Out of scope: searching by value, range queries, transactions across keys.

Non-functional requirements

  • Fast. Other systems call it on every request, so lookups take a few milliseconds.
  • Scalable. Data and traffic outgrow one machine, so we must add machines easily.
  • Always available. Machines fail often. Reads and writes must keep working, even if a read is briefly stale.

Core entities

  • Entry: a key, its value, and a version number that says which write is newest.
  • Node: one storage machine that holds a slice of the entries.

API design

PUT/keys/{key}

Saves or overwrites a value. Over 1 MB (assumed) gets 413.

Request body
{ "value": "dark_mode=on" }
Response 200 OK
{ "version": 1731200000123 }

Returns the newest value. A missing or deleted key gets 404.

  "version": 1731200000123 }
DELETE/keys/{key}

Saves a tombstone instead of erasing, and cleans it up later. Deleting twice is fine.

(none)
Response 204 No Content

High-level design

Assume 100 million entries of about 1 KB each: 100 GB, and 20,000 requests a second at peak. One machine could hold that, but it would be a single point of failure. We start with one node, then spread out.

1. Save, get and delete on one node

The app servers (identical, no data of their own, behind a load balancer) pass each call to the node. A node appends every change to a log file on disk first, then updates an in-memory lookup table. After a crash it replays the log. A hash-table lookup is one step, which answers "fast". The client picks the key, so no ID generator is needed. The version is the server time in milliseconds, and the newest wins.

Per node: entries
ColumnTypeNote
keytextprimary key (hash lookup)
value, versionbytes, bigintvalue is null for a tombstone

2. Spread over many nodes

We split the keys between nodes and copy each key to three of them, as the deep dives explain.

Why

Why not a normal SQL database? We only look up by key, so we need no joins or queries. Dropping them keeps every request one cheap step and makes spreading over machines easier.

Deep dives

How do we spread keys over many machines?

Each key needs a clear owner, and adding a machine should not reshuffle everything.

  1. Hash, then mod by machine count. Even spread, but adding one machine moves almost every key.
  2. Ranges of keys (A-F, G-M…). Easy to read, but popular ranges overload one machine.
  3. Hash ring.Pick Adding a machine moves only a small share of keys.

On a hash ring, a key goes to the first node clockwise from its hash. A new node takes over only the keys just before it. Each node sits at many points (virtual nodes, say 100) to even out the load. The services keep the ring in memory, so each call goes straight to the owner.

How do we stay up when a machine dies?

A dead node must not lose keys.

  1. One copy per key. Simple, but data is lost when a node dies.
  2. One primary plus a backup that is promoted on failure. Reads are always fresh, but writes stall during the switch.
  3. Three copies with a quorum.Pick Survives one dead node, and never stops.

A key is copied to its owner and the next two nodes on the ring, which are its replicas. A write goes to all three and succeeds once 2 confirm. A read asks 2 and returns the newer version. Any 2 writers and 2 readers out of 3 overlap, so a read sees the latest write. A node that missed a write is fixed when next read.

Final design

The dives added the ring and three-way copies. Services are split by job: the Write API stamps versions and waits for 2 confirmations, while the Read API compares two copies. Reads usually outnumber writes, so the read side scales alone. An API gateway routes by path and method.

A quorum of 2 copes with one node down. If two of a key's nodes are down, writes to it fail with 503 rather than risk losing data. Rare stale reads are fine for settings and sessions, not for money.

What you could add next

  • A background repair job that compares copies and fixes differences.
  • A key expiry (TTL) so old entries delete themselves.
  • A small cache in front of very popular keys.

Interview tips

What if a node is down during a write?
The other two confirm and the write succeeds. The missed node is fixed later.
How do two writes to one key get ordered?
By version, newest wins. Clocks can drift, so some systems use vector clocks.
How do you add a node?
Put it on the ring. It copies its share of keys from its neighbours, and only those keys move.

Common mistakes

  • Using hash mod N, so adding a node moves almost every key.
  • Erasing a deleted key instead of saving a tombstone, so an old copy brings it back.
Interview tip

State the trade-off aloud: we chose availability, so reads may be slightly stale.

Confidence note

The traffic, value limit and 100 virtual nodes are assumptions. Strict consistency (one primary per key) is also a valid answer, and it fits when stale reads are not acceptable.

Sources: DeCandia et al., Dynamo: Amazon's Highly Available Key-value Store (a published design, not a claim about today's systems); Alex Xu, System Design Interview, chapter "Design a Key-Value Store"; Hello Interview's system design delivery framework.

Design a job scheduler

You say "send this report every Monday at 9" and it just happens, even if a server dies on the way. The interview asks how to start many jobs on time without losing them or running them twice.

Features Qualities Entities API Design Deep dives Tips
Legend 7 terms used below
Cron expression
A short text rule for repeating times. "0 9 * * 1" means 9:00 every Monday.
Queue
A waiting line of messages. One part adds messages, another takes them off when it is ready.
Worker
A background program that takes a message from a queue and does the work in it.
At-least-once delivery
The queue keeps a message until a worker confirms it finished. A message is never lost, but it may arrive twice.
Idempotent
Safe to do twice. The second time changes nothing.
API gateway
The single front door of a system. It sends each request to the right service.
Replica
A kept-up-to-date copy of a database that takes over if the main copy (the primary) dies.

Functional requirements

  • Create a job that runs once at a set time, or repeats on a cron expression.
  • See a job's status and its past runs.
  • Cancel a job.

Out of scope: jobs that wait on other jobs, and tasks that run for hours.

Non-functional requirements

  • On time. A 9:00 job should start within seconds, even when thousands are due together.
  • Never lost. A due job must still run if a server crashes.
  • Not run twice. A double email or double charge is a real bug.

Core entities

  • Job: what to run, its schedule and when it is next due.
  • Run: one attempt to run a job, with start time and outcome.

API design

POST/jobs

Creates a job. Use run_at instead of schedule for a one-off. A bad schedule gets 400.

High-level design

Assume 10 million jobs and 1 million runs a day: about 12 a second, so one database copes. The risk is a burst at midnight. The API is identical app servers that keep no data, behind a load balancer. Job IDs come from a Snowflake-style generator.

1. Create a job

The app server checks the schedule, works out the first next_run_at and saves one row.

Table: jobs
ColumnTypeNote
job_idbigintprimary key
owner_id, schedule, payloadtext, text, jsonwho, when, what to run
next_run_attimestamp (UTC)index on (status, next_run_at)

Table: runs
ColumnTypeNote
run_idtextprimary key: job_id + due time
job_id, outcome, triesbigint, text, intindex on (job_id, due time) for the status page

2. Find jobs that are due

A scheduler process wakes every second and asks for rows where status = 'active' and next_run_at <= now. The index means it reads only due rows. For each, it moves next_run_at to the next cron time, or marks a one-off done.

3. Run them

The scheduler puts "run job X" on a queue. Workers take messages, run the task and save a run row. Add workers for a burst.

Why

Why a queue between the scheduler and the workers? The scheduler only decides what is due, which is quick. If it ran tasks itself, one slow task would make every other job late.

Deep dives

How do we never lose a job, and not run it twice?

Servers can crash at any step.

  1. Run the task inside the scheduler. Simplest, but a crash loses the job.
  2. Queue with at-least-once delivery.Pick Never lost, but a message may arrive twice.
  3. Try for exactly-once with distributed transactions. Slow and hard to get right.

With at-least-once delivery, a message stays hidden while a worker holds it. If the worker dies, it reappears after a timeout (5 minutes, assumed). A duplicate is harmless if the task is idempotent. The run_id is the job plus its due time, and a worker skips any run_id already succeeded. Failed runs retry 3 times with growing waits.

How do we start jobs on time when many are due at once?

One scheduler can fail or fall behind.

  1. One scheduler polling the database. Simple, but it stops if it dies.
  2. Several schedulers claiming batches with row locks.Pick No single point of failure, and they split the work.
  3. One in-memory timer per job. Exact, but lost on restart and heavy on memory.

Run two or three schedulers (assumed). Each second, one selects up to 500 due rows with FOR UPDATE SKIP LOCKED, which skips rows another scheduler holds. It enqueues them, moves next_run_at and commits. A crash before the commit releases the locks, so at worst a job is queued twice, which the run_id check handles.

Final design

The dives added run_id checks and several locking schedulers. Services are split by job: the Job API takes writes, the Status API reads from the replica, and the scheduler and workers run in the background so they never slow the API. An API gateway routes by path.

If the primary dies, the replica takes over. If the queue is down, due jobs stay due and run late. Status may be a second stale; claiming jobs always uses the primary.

What you could add next

  • A dead-letter queue for jobs that keep failing, with an alert.
  • Priorities, so urgent jobs skip ahead of bulk ones.
  • Split the jobs table across several databases by job_id when one is not enough.

Interview tips

What if a task outlives the queue timeout?
Set it longer than the slowest task, or let the worker keep extending it.
How do you handle time zones?
Store next_run_at in UTC and keep the zone with the schedule.
A million jobs are due at midnight. Now what?
The queue absorbs it and workers scale up. Add jitter where exact seconds don't matter.

Common mistakes

  • Scanning the whole table each second instead of using an index on next_run_at.
  • Running tasks inside the scheduler, so one slow job delays all others.
Interview tip

Say "at-least-once delivery plus idempotent tasks" out loud.

Confidence note

The traffic, 5-minute timeout, batch size and scheduler count are assumptions. Other designs use a Redis sorted set or a timing wheel instead of database polling, and both are valid.

Design a unique ID generator

Every order, message and photo needs its own number, and no two may ever match. The interview asks how to do it on many machines at once without collisions.

Features Qualities Entities API Design Deep dives Tips
Legend 7 terms used below
Auto-increment
A database counter that gives each new row the next number: 1, 2, 3 and so on.
Snowflake-style ID
A 64-bit number built from the current time, a machine number and a counter, so machines can make IDs on their own.
Bit
One 0 or 1. A 64-bit number has 64 of them, and each extra bit doubles how many values fit.
Epoch
The starting moment we count time from. We pick our own recent date so the time part stays small.
Lease
A claim on something that expires unless renewed. A machine that stops renewing loses its claim.
API gateway
The single front door of a system. It sends each request to the right service.
Replica
A kept-up-to-date copy of a database that takes over if the main copy (the primary) dies.

Functional requirements

  • Ask for a new ID that has never been given out.
  • IDs sort roughly by creation time, so newer means bigger.
  • Read an ID to see when and where it was made.

Out of scope: IDs with no gaps, exact order across machines, and hiding IDs from guessers.

Non-functional requirements

  • Never a duplicate. Two rows sharing an ID corrupt data.
  • Always available and fast. Every write in the company waits for an ID.
  • Small and sortable. A 64-bit number fits a normal database column and sorts quickly.

Core entities

  • ID: one 64-bit number, made of a time, a machine number and a counter.
  • Machine registry row: which machine number belongs to which running server.

API design

POST/ids

Makes one new ID. If the server's clock went backwards and it cannot be sure of uniqueness, it answers 503 and the caller retries.

Request body
(none)
Response 201 Created
{
  "id": "7192837465019392"
}
GET/ids/{id}

Splits an ID into its parts. A value that is not a valid number gets 400.

Request body
(none)
Response 200 OK
{
  "created_at": "2026-11-08T04:00:00.123Z",
  "machine_id": 17,
  "sequence": 5
}

High-level design

Assume 100,000 IDs a second across the company. The API is identical app servers that keep no user data, behind a load balancer.

1. The obvious start

One database with auto-increment hands out 1, 2, 3. It is unique and sorted, but every ID costs a database round trip, and if that database dies nobody can get an ID.

2. Let each machine make its own

A Snowflake-style ID packs three parts into 64 bits. Two machines can never match, because their machine numbers differ, and one machine never repeats, because its time or its counter always moves on. No talking between machines is needed per ID.

ID layout (64 bits)
PartBitsNote
sign1always 0, so the number stays positive
time41milliseconds since our own epoch; 2^41 ms is about 69 years
machine10up to 1,024 generators
sequence12counts 0-4,095 within one millisecond

One machine can make 4,096 IDs per millisecond, about 4 million a second, so three machines already cover 100,000 a second. Time goes in the high bits, so bigger means newer. Machine numbers come from a small registry.

Why

Why not one counter in a database? It is one slow, shared point that everyone waits on. Building the ID from the clock needs no one's permission.

Deep dives

How do we guarantee two machines never make the same ID?

Uniqueness is the whole point, so machine numbers must never be shared by two running servers.

  1. Random UUID. No coordination, but 128 bits and not sorted by time, which makes database indexes slower.
  2. Ticket server (one database counter). Simple, but a bottleneck and a single point of failure.
  3. Snowflake-style with a leased machine number.Pick Small, sorted, and no per-ID coordination.

On start, a server claims a free row in the registry and gets a lease of 30 seconds (assumed). It renews every 10 seconds. If it dies, the lease runs out and the number can be handed to a new server. Without a valid lease it makes no IDs.

How do we handle clock problems?

The design trusts the clock, and clocks sometimes jump back after a time sync.

  1. Ignore it. Fast, but after a jump back the server could repeat an old time and make a duplicate.
  2. Remember the last time used and refuse to go back.Pick Costs a tiny wait or an error, never a duplicate.
  3. Check the time with a central clock service. More exact, but slow and one more thing to fail.

The server keeps the last millisecond it used in memory. If the clock is only a few milliseconds behind, it waits. If further behind, it returns 503 and the load balancer retries another server. If all 4,096 counter values in one millisecond are used, it waits for the next millisecond.

Final design

The dives added the leased machine number and the clock guard. The API gateway splits the two jobs: creating IDs is hot and must scale on its own, while decoding is rare and needs no registry.

The registry has a replica that takes over if the primary dies. If the registry is down, running generators keep going on their current lease; only new servers wait.

What you could add next

  • Hand out IDs in blocks so callers can make a batch locally.
  • Spread generators over several data centres with a data-centre bit.
  • Add a checksum or shuffle so IDs are hard to guess.

Interview tips

What if you need more than 4,096 IDs per millisecond per machine?
Add more machines, or shift a bit or two from the machine part to the sequence.
Why not just use a UUID?
It is twice as big and unsorted, so index inserts are slower.
What happens when the 41 time bits run out?
After about 69 years from our epoch. Choose a recent epoch.

Common mistakes

  • Forgetting that clocks can jump backwards.
  • Giving two running servers the same machine number.
Interview tip

Draw the 64-bit layout early and say what each part guarantees. It answers most follow-ups.

Confidence note

The traffic, the 30-second lease and the exact bit split are assumptions. The 41/10/12 split is a common choice, and other splits are valid.

Design photo sharing

People upload photos, and other people open them. Photos are big files and are viewed far more often than they are uploaded, so the interview is about moving files without clogging your servers.

Features Qualities Entities API Design Deep dives Tips
Legend 7 terms used below
Blob storage
A service that keeps big files (like photos) cheaply, each under a key. It stores several copies, so one broken disk loses nothing.
Pre-signed URL
A temporary link, made by our server, that lets a user upload or download one file straight from storage.
API gateway
The single front door of a system. It receives every request and sends each one to the right service.
CDN
A network of servers around the world that keep copies of files, so each viewer gets them from a nearby machine.
Queue
A line of messages waiting to be handled, in order. The sender drops a message in and moves on without waiting.
Worker
A background program that takes messages from a queue and does the work.
Replica
A copy of a database that is kept up to date. It takes over if the main copy (the primary) dies.

Functional requirements

  • Upload a photo with a caption.
  • Open one photo.
  • See a user's photos, newest first.

Out of scope: the news feed, likes, comments, follows and video.

Non-functional requirements

  • Fast to open. Viewers outnumber uploaders by far, and slow images make them leave.
  • Never lose a photo. Photos are memories.
  • Uploads must not hog servers. A photo is megabytes, so pushing it through our servers would choke them.

Core entities

  • Photo row: its id, owner, caption, status and where the file lives.
  • Photo file: the image itself, plus a small thumbnail.

API design

POST/photos

Creates the photo row and returns a link. The browser then sends the file itself to that link with PUT. Over 10 MB (assumed) or not JPEG/PNG gets 400.

How do we take 6,000 clicks a second without slowing users or losing clicks?

  2. Count in the service's memory and flush every few seconds. Fast, but a crash loses those seconds of clicks.

  1. Copy to everyone. Simple, but one post clogs the queue for minutes.
  2. Copy for ordinary accounts, merge for big ones.Pick Skip the copy for accounts over 100,000 followers (an assumed cut-off). When a feed is loaded, also fetch the latest posts of the few big accounts that user follows, and merge them by post_id.

The worker checks follower_count before copying. Most people follow only a few big accounts, so the extra work on read is small.

Final design

The dives added a queue, fan-out workers, a feed cache and the big-account rule. The API gateway splits traffic by job: posts are rare, feed loads constant, and a fan-out burst must never slow a feed load.

A post is saved on the primary before the app says "posted". Feed reads use a replica, which may be a moment behind. That is fine for a feed. If the primary dies, the replica takes over.

TTL
Time to live. How long a cache entry may stay before it is deleted automatically.

Functional requirements

  • Paste some text and get back a short link.
  • Open the link to read that text.
  • Optionally choose when a paste expires.

Out of scope: accounts, editing a paste, syntax colours, search.

Non-functional requirements

  • Fast reads. A link is opened many more times than it is created, so opening must feel instant.
  • Durable. People share logs and code. A paste must not vanish before it expires.
  • Unique, hard-to-guess links. Two pastes must never share a link, and a stranger should not be able to guess yours.

Core entities

  • Paste: a small record with the id, created time, expiry time and where its text is kept.
  • Text: the pasted content itself, capped at 1 MB (an assumed limit).

API design

POST/pastes

Create a paste. Text over 1 MB is rejected with 413 Content Too Large.

High-level design

Assume the usual setup: identical app servers that keep no data, behind a load balancer. Assume 1 million new pastes a day (about 12 a second) and 10 reads per paste (about 120 a second). At 10 KB each, that is 10 GB of new text a day, so the text stays out of the database.

1. Creating a paste

The server makes an 8-character id from 62 symbols (a-z, A-Z, 0-9). That gives about 218 trillion ids, so a random one is almost never taken; if the database refuses a duplicate key, we draw again. Then it saves the text and a small row, and returns 201.

2. Reading a paste

Look up the row by id. No row means 404. An expires_at in the past means 410. Otherwise fetch the text by its key and return 200.

Why

Why a random id and not a counter? A counter (1, 2, 3...) lets anyone read every paste by counting up. Random ids keep pastes unlisted, at the price of a rare retry.

Deep dives

Where do we keep the text so it is not lost?

Ten GB a day must be cheap to store and safe.

  1. In the database row. One place to look, but the database swells and backups slow down.
  2. On the app server's disk. Cheap, but other servers cannot see it and a dead disk loses pastes.
  3. Blob storage.Pick A blob store keeps copies for us and is built for big files. The database keeps only the small row with the key.

Pastes never change, which suits write-once files. With a 1 MB cap the write service can pass the text on itself; pre-signed upload URLs only pay off for much larger files.

How do we keep reads fast?

Reads outnumber writes ten to one, and one popular paste may be opened thousands of times.

  1. Always ask the database and blob store. Simple, but every read costs two calls.
  2. Add a cache.Pick The read service checks a cache first (paste id to text and expiry). On a miss it loads from the replica and blob store, then fills the cache.
  3. Add a CDN. Great worldwide, but more setup than a first design needs.

An entry gets a TTL of one hour, or the time left until the paste expires if that is sooner, so an expired paste is never served.

Final design

The dives added blob storage and a cache. The API gateway splits traffic by job: new pastes are about 12 a second, reads about ten times that, so the read side can be scaled on its own.

If the primary database dies, its replica takes over; the blob store keeps its own copies. If the cache goes down, reads fall back to the database and blob store: slower, but correct.

What you could add next

  • A nightly job that deletes expired rows and their text, so storage stops growing.
  • A CDN in front of reads for readers far from the servers.
  • Split the database by id (sharding) once one primary can't keep up.

Interview tips

What if two pastes get the same id?
The primary key rejects the second insert, and the write service retries with a new random id.
Why not store the text in the database?
Big text bloats the database and its backups. A blob store is cheaper and built for it.
What about a 500 MB paste?
Cap pastes at 1 MB and return 413. Bigger files would use a pre-signed URL, so the upload goes straight to blob storage.

Common mistakes

  • Using 1, 2, 3... as ids, so anyone can read every paste by counting.
  • Returning 404 for an expired paste, which hides the difference between "gone" and "never existed".
Interview tip

Say early that you split a small record from a big blob, and why.

Confidence note

The traffic numbers and 1 MB cap are assumptions. A random id and a key-generator service are both accepted. A replica can rarely miss a brand-new paste; retrying on the primary fixes it.

Design a rate limiter

A free weather API lets each app make 100 calls a minute. Call 101 gets a polite "slow down". A rate limiter is that bouncer. The feature is tiny, but it tests counting, sharing one count across servers, and what happens when the counter breaks.

Features Qualities Entities API Design Deep dives Tips
Legend 7 terms used below
Rate limit
The most requests a client may send in a period of time, for example 100 per minute.
429
The HTTP status code "Too Many Requests". It tells the client it was blocked for sending too much, not that the server is broken.
API gateway
The single front door of a system. It receives every request and sends each one to the right service.
Token bucket
A counting method: a bucket holds tokens, each request takes one, and tokens drip back in at a steady speed. No token means no request.
Redis
A very fast database that keeps its data in memory. It is often used for counters and caches.
Atomic
Done as one indivisible step. Nothing else can sneak in halfway through.
Fail open
When a safety check breaks, let requests through instead of blocking everyone.

Functional requirements

  • Limit how many requests one client can make in a time window, per user (or per IP when not logged in).
  • Reject extra requests with a clear error that says when to try again.
  • Let admins set different limits for different endpoints.

Out of scope: defending against large attacks (DDoS), paid pricing tiers, per-country rules.

Non-functional requirements

  • Fast. The check runs on every single request, so it may add only a few milliseconds.
  • Same limit on every server. If each server counts alone, five servers allow five times the limit.
  • Available. A broken limiter must not take the API down with it.

Core entities

  • Rule: an endpoint, how many requests it allows, and over how many seconds.
  • Bucket: one per client and endpoint, holding how many tokens are left and when it last refilled.

API design

GET/weather

Any protected endpoint. The limiter sits in front of all of them and adds headers.

Response 200 OK
X-RateLimit-Remaining: 42
{ "temp_c": 27 }
Response 429 Too Many Requests
Retry-After: 12
{ "error": "rate_limited" }
PUT/rules/{endpoint}

Admin only. Create or replace the limit for one endpoint.

Request body
{
  "limit": 100,
  "window_seconds": 60
}
Response 200 OK
{ "endpoint": "weather" }

High-level design

We build it one requirement at a time. Assume the usual setup: identical servers that keep no data, behind a load balancer.

1. Limiting a client

Every request first meets the limiter. It builds a key from the user id in the auth token plus the endpoint (the IP if there is no token) and asks a shared counter store whether to go ahead. If not, the client gets a 429 with a Retry-After header.

Counters must be shared, so they live in Redis, not in each server's memory. Assume 10,000 requests a second. That is 10,000 Redis calls a second, and one Redis handles roughly 100,000, so one primary is enough. A million clients at about 100 bytes each is only 100 MB.

2. Different limits per endpoint

Admins call PUT /rules/{endpoint} and we save a row. Rules change rarely, so the limiter keeps a copy in memory and refreshes it every minute.

Table: rules
ColumnTypeNote
endpointtextprimary key, e.g. weather
limitintrequests allowed per window
window_secondsintlength of the window
Why

Why block at the front? Turning a request away costs one cheap lookup; letting it in costs the full work of the API. And 429 tells the client the problem is its own speed.

Deep dives

How do we count requests?

Three common ways to decide if one more request fits:

  1. Fixed window. One counter per client per minute, reset when the minute ends. Simple, but 100 requests at 12:00:59 plus 100 at 12:01:00 means 200 in two seconds.
  2. Sliding log. Store the time of every request and count those in the last minute. Exact, but memory-hungry.
  3. Token bucket.Pick A bucket holds up to 100 tokens and refills at 100 per minute. Each request takes one token; empty means 429. Short bursts are fine, the long-run rate stays capped, and we store just two numbers.

No timer is needed: each request works out from last_refill how many tokens dripped in, and adds them.

How do we count correctly across servers?

Two servers may touch the same bucket in the same instant.

  1. Count in each server's memory. Fast, but the limit multiplies by the server count.
  2. Shared Redis, read then write. Two servers both read "1 token left" and both allow.
  3. Shared Redis, one atomic step.Pick A short Lua script inside Redis reads, refills, takes a token and writes back. Redis runs one script at a time, so it is atomic. Cost: one hop of about a millisecond.

Give each bucket key an expiry (TTL) of about a full refill. An idle bucket is full anyway, so deleting it loses nothing.

Final design

The dives added atomic token buckets in Redis. The gateway routes by path to services split by job: the limit service sits on every request, while the rules service handles rare admin changes.

Redis has a replica that takes over if the primary dies, and the rules database has one too. If Redis is still unreachable, the limiter fails open: requests pass and an alert fires.

What you could add next

  • Different limits for free and paid users.
  • Split Redis by client key (sharding) once one primary can't keep up.
  • Let each limiter server allow a few requests from a local count first, to cut Redis calls.

Interview tips

Limit by user or by IP?
User id from the token if present, else IP (an office can share one IP).
Where should the limiter live?
In the gateway, so every service is covered in one place.
What if Redis goes down?
Fail open and alert; for login attempts you may fail closed.

Common mistakes

  • Counting in each server's memory, so the real limit grows with the server count.
  • Reading the count and writing it back as two steps, which lets a burst slip through.
  • Rejecting with no Retry-After, so clients retry at once.
Interview tip

Name two or three counting methods, pick one, and say what you give up. That comparison is the heart of this question.

Confidence note

The traffic numbers (10,000 requests a second, a million clients) are assumptions. All three counting methods are accepted; explain the trade-off and keep counting atomic.

Design a URL shortener

You paste a long link and get back something tiny like sho.rt/x7Kp2Q. Anyone who opens the tiny link lands on the original page. It is the classic first system design question: small enough for one interview, yet it still covers unique IDs, caching and staying online.

Legend 10 terms used below

A copy of the database that is kept up to date with the main one. If the main one dies, a replica can take over.

Functional requirements

  • Submit a long URL and get a short one back.
  • Opening the short URL takes you to the original site.
  • Optional: pick a custom alias (sho.rt/my-party) or an expiry date.

Out of scope: user accounts, click analytics, spam and malware filtering.

Non-functional requirements

  • Unique short codes. One code must point to exactly one long URL, or people land on the wrong site.
  • Fast redirects. A short link stands between a person and the page they want, so the extra hop should feel instant (a common target is under about 100 ms).
  • High availability. If it goes down, every short link ever shared breaks at once. A brand-new link may take a moment to work everywhere; old links must keep working.
  • Built for reads. A link is created once but may be opened thousands of times, so reads far outnumber writes.

Core entities

  • Link: the short code, the original long URL, when it was made and (optionally) when it expires.
  • User: who created the link. Only needed once we add accounts, which is out of scope today.

API design

One endpoint per functional requirement is enough.

High-level design

We build it one requirement at a time, simplest version first. I'll assume the usual setup: a few identical app servers that keep no data of their own, behind a load balancer.

1. Creating a short link

The client sends POST /urls. An app server checks the long URL looks valid, makes a new short code (first deep dive), saves the pair in the database and returns the short link.

Table: links
ColumnTypeNote
short_codetextprimary key, e.g. x7Kp2Q

expires_attimestamp, optionalempty means never

Because short_code is the primary key, finding a link by its code stays fast even with billions of rows.

Do we need several databases? Say 100M new links a month, which is about 40 per second. At roughly 500 bytes a row, that is 50 GB a month, or about 600 GB a year. One database server handles both easily, so we don't split the data yet.

2. Following a short link

Someone opens sho.rt/x7Kp2Q, so their browser sends GET /x7Kp2Q. The app server looks up the code and replies with status 302 and a Location header holding the long URL. The browser follows it on its own. Unknown codes get 404, expired ones get 410.

Why

Why 302 and not 301? A 301 means "moved permanently", so browsers remember it and skip us on later clicks. That saves traffic but costs control: we can't expire a link, change it, or count clicks. A 302 ("temporarily over there") sends every click back through us. More traffic, which is why the next deep dive is about speed.

Deep dives

How do we keep short codes unique?

We need a short string nobody else already has. Three common approaches:

  1. Use part of the long URL. Take its first few characters. Many URLs start with https://www., so codes clash constantly. Not workable.
  2. Hash the long URL. Run it through a hash function such as SHA-256, write the result in base62, and keep the first 7 characters. The same URL always gives the same code. But two different URLs can occasionally share those 7 characters, so we must check the database and retry with a tweak when that happens.
  3. Count.Pick One counter hands out the next number: 1, 2, 3 and so on. Each new link takes a number and writes it in base62, so 125 becomes 21 (2 × 62 + 1). Two links can never get the same number, so there is nothing to check. An in-memory store like Redis can increase a counter safely for this, even with many app servers asking at once.

I'd pick the counter, because uniqueness comes from the design itself, with no retry logic. Is 7 characters enough? 627 is about 3.5 trillion codes. At 100M links a month we use about 1.2 billion a year, so we would last thousands of years.

The downside: codes come out in order, so neighbouring links are guessable. If that matters, scramble the number with a reversible step before encoding. One counter is no bottleneck at about 40 new numbers a second, and the unique primary key stays as a safety net if it ever repeats a number after a crash.

How do we keep redirects fast?

Every click is a read. If each link is opened about 100 times, our 40 new links a second become about 4,000 redirects a second on average, and several times that at busy moments.

  1. Just the database. A lookup by primary key already takes only a few milliseconds. Fine to start, but every click lands on the database.
  2. Add a cache in front.Pick Keep popular code-to-URL pairs in a cache such as Redis. The app server checks the cache first; on a miss it reads the database and saves the answer for next time. Memory lookups take well under a millisecond, and clicks tend to bunch up on a small set of popular links, so most requests never reach the database.
  3. Cache close to users. Answer redirects from a CDN. Fastest, but harder to expire links or count clicks. A "later" idea.

When a link expires or changes, delete its cache entry too, and never let a cached entry outlive the link's own expiry date.

How do we stay available?

App servers are interchangeable, so losing one is no big deal. The scary failure is the database: if the only copy dies, every redirect fails.

  1. One database plus backups. Cheap, but restoring can take hours, with every link broken meanwhile.
  2. A primary with replicas.Pick Every write goes to the primary and is copied to one or two replicas. If the primary dies, a replica is promoted to take its place. Replicas can also answer redirect lookups.
  3. Copies in several regions. Survives a whole region going offline, at a big cost in complexity. Later, if ever.

Replicas lag a moment behind, so a brand-new link might be missing from one for a fraction of a second. That is the trade we accepted: availability first, perfectly fresh data second.

Final design

Putting the deep dives together gives the complete picture: a counter for unique codes, a cache for fast redirects, and a replica so one database failure doesn't break every link. One change from the first sketch: an API gateway, the single front door that sends each request to the right service, splits the work into a write service and a read service. Clicks vastly outnumber new links, so the read side can be run and scaled on its own.

What you could add next

  • Serve the most popular redirects from a CDN.
  • Hand each write-service instance a block of 1,000 counter values at once, so it rarely asks the counter.
  • Click analytics: record each click in a log that a background job counts later, so redirects stay fast.
  • Split the links table across several databases by short code (called sharding) once it outgrows one machine.

Interview tips

Why 302 instead of 301?
A 302 keeps every click coming through us, so we can expire, change or count links. Browsers cache a 301 and stop asking.
Two people shorten the same URL. Same code?
Not necessarily. A new code each time is simpler; de-duplicate only if asked (hashing gives it for free).
How do custom aliases work?
Check the alias is free (the unique primary key enforces it), and keep aliases in their own space, like sho.rt/c/my-party, so a generated code can never land on one.

Common mistakes

  • Jumping to sharding, queues and microservices before the basic create and redirect flow works.
  • Ignoring the read/write imbalance. Reads outnumber writes by a lot, so the cache is where design effort pays off.
Interview tip

Say the read/write ratio out loud early. It is the one number that justifies the cache, and interviewers listen for it.

Confidence note

The traffic numbers here (100M new links a month, about 100 clicks per link) are assumptions to make the math concrete. Your interviewer may give others. Hashing and counting are both accepted answers; what matters is explaining how you avoid clashes.
