Design a rate limiter

A free weather API lets each app make 100 calls a minute. Call 101 gets a polite "slow down". A rate limiter is that bouncer. The feature is tiny, but it tests counting, sharing one count across servers, and what happens when the counter breaks.

Features Qualities Entities API Design Deep dives Tips
Legend 7 terms used below
Rate limit
The most requests a client may send in a period of time, for example 100 per minute.
429
The HTTP status code "Too Many Requests". It tells the client it was blocked for sending too much, not that the server is broken.
API gateway
The single front door of a system. It receives every request and sends each one to the right service.
Token bucket
A counting method: a bucket holds tokens, each request takes one, and tokens drip back in at a steady speed. No token means no request.
Redis
A very fast database that keeps its data in memory. It is often used for counters and caches.
Atomic
Done as one indivisible step. Nothing else can sneak in halfway through.
Fail open
When a safety check breaks, let requests through instead of blocking everyone.

Functional requirements

  • Limit how many requests one client can make in a time window, per user (or per IP when not logged in).
  • Reject extra requests with a clear error that says when to try again.
  • Let admins set different limits for different endpoints.

Out of scope: defending against large attacks (DDoS), paid pricing tiers, per-country rules.

Non-functional requirements

  • Fast. The check runs on every single request, so it may add only a few milliseconds.
  • Same limit on every server. If each server counts alone, five servers allow five times the limit.
  • Available. A broken limiter must not take the API down with it.

Core entities

  • Rule: an endpoint, how many requests it allows, and over how many seconds.
  • Bucket: one per client and endpoint, holding how many tokens are left and when it last refilled.

API design

GET/weather

Any protected endpoint. The limiter sits in front of all of them and adds headers.

Response 200 OK
X-RateLimit-Remaining: 42
{ "temp_c": 27 }
Response 429 Too Many Requests
Retry-After: 12
{ "error": "rate_limited" }
PUT/rules/{endpoint}

Admin only. Create or replace the limit for one endpoint.

Request body
{
  "limit": 100,
  "window_seconds": 60
}
Response 200 OK
{ "endpoint": "weather" }

High-level design

We build it one requirement at a time. Assume the usual setup: identical servers that keep no data, behind a load balancer.

1. Limiting a client

Every request first meets the limiter. It builds a key from the user id in the auth token plus the endpoint (the IP if there is no token) and asks a shared counter store whether to go ahead. If not, the client gets a 429 with a Retry-After header.

Counters must be shared, so they live in Redis, not in each server's memory. Assume 10,000 requests a second. That is 10,000 Redis calls a second, and one Redis handles roughly 100,000, so one primary is enough. A million clients at about 100 bytes each is only 100 MB.

2. Different limits per endpoint

Admins call PUT /rules/{endpoint} and we save a row. Rules change rarely, so the limiter keeps a copy in memory and refreshes it every minute.

Table: rules
ColumnTypeNote
endpointtextprimary key, e.g. weather
limitintrequests allowed per window
window_secondsintlength of the window
Why

Why block at the front? Turning a request away costs one cheap lookup; letting it in costs the full work of the API. And 429 tells the client the problem is its own speed.

Deep dives

How do we count requests?

Three common ways to decide if one more request fits:

  1. Fixed window. One counter per client per minute, reset when the minute ends. Simple, but 100 requests at 12:00:59 plus 100 at 12:01:00 means 200 in two seconds.
  2. Sliding log. Store the time of every request and count those in the last minute. Exact, but memory-hungry.
  3. Token bucket.Pick A bucket holds up to 100 tokens and refills at 100 per minute. Each request takes one token; empty means 429. Short bursts are fine, the long-run rate stays capped, and we store just two numbers.

No timer is needed: each request works out from last_refill how many tokens dripped in, and adds them.

How do we count correctly across servers?

Two servers may touch the same bucket in the same instant.

  1. Count in each server's memory. Fast, but the limit multiplies by the server count.
  2. Shared Redis, read then write. Two servers both read "1 token left" and both allow.
  3. Shared Redis, one atomic step.Pick A short Lua script inside Redis reads, refills, takes a token and writes back. Redis runs one script at a time, so it is atomic. Cost: one hop of about a millisecond.

Give each bucket key an expiry (TTL) of about a full refill. An idle bucket is full anyway, so deleting it loses nothing.

Final design

The dives added atomic token buckets in Redis. The gateway routes by path to services split by job: the limit service sits on every request, while the rules service handles rare admin changes.

Redis has a replica that takes over if the primary dies, and the rules database has one too. If Redis is still unreachable, the limiter fails open: requests pass and an alert fires.

What you could add next

  • Different limits for free and paid users.
  • Split Redis by client key (sharding) once one primary can't keep up.
  • Let each limiter server allow a few requests from a local count first, to cut Redis calls.

Interview tips

Limit by user or by IP?
User id from the token if present, else IP (an office can share one IP).
Where should the limiter live?
In the gateway, so every service is covered in one place.
What if Redis goes down?
Fail open and alert; for login attempts you may fail closed.

Common mistakes

  • Counting in each server's memory, so the real limit grows with the server count.
  • Reading the count and writing it back as two steps, which lets a burst slip through.
  • Rejecting with no Retry-After, so clients retry at once.
Interview tip

Name two or three counting methods, pick one, and say what you give up. That comparison is the heart of this question.

Confidence note

The traffic numbers (10,000 requests a second, a million clients) are assumptions. All three counting methods are accepted; explain the trade-off and keep counting atomic.

Design a URL shortener

You paste a long link and get back something tiny like sho.rt/x7Kp2Q. Anyone who opens the tiny link lands on the original page. It is the classic first system design question: small enough for one interview, yet it still covers unique IDs, caching and staying online.

Features Qualities Entities API Design Deep dives Tips
Legend 10 terms used below
Short code
The few characters at the end of a short link, like x7Kp2Q. It is the key we use to find the original URL.
Redirect
A reply from a server that says "what you want is over there" and gives the browser a new address to load instead.
Availability
How much of the time a system is up and answering. "Highly available" means it almost never goes down.
Endpoint
One address plus HTTP method that a server answers, like POST /urls. Together, the endpoints make up the API.
Load balancer
A machine that receives all incoming requests and spreads them across several app servers, so no single one gets overloaded.
Primary key
The column a table is organised by. The database keeps an index on it, so finding a row by its key is fast, even among billions.
Base62
Writing a number with 62 symbols (0-9, a-z, A-Z) instead of 10 digits, so big numbers turn into short strings.
Cache
A small, very fast store that keeps copies of popular data in memory, so most requests can skip the slower database.
CDN
Content delivery network: servers spread around the world that keep copies of answers close to users, so responses travel less distance.
Replica
A copy of the database that is kept up to date with the main one. If the main one dies, a replica can take over.

Functional requirements

  • Submit a long URL and get a short one back.
  • Opening the short URL takes you to the original site.
  • Optional: pick a custom alias (sho.rt/my-party) or an expiry date.

Out of scope: user accounts, click analytics, spam and malware filtering.

Non-functional requirements

  • Unique short codes. One code must point to exactly one long URL, or people land on the wrong site.
  • Fast redirects. A short link stands between a person and the page they want, so the extra hop should feel instant (a common target is under about 100 ms).
  • High availability. If it goes down, every short link ever shared breaks at once. A brand-new link may take a moment to work everywhere; old links must keep working.
  • Built for reads. A link is created once but may be opened thousands of times, so reads far outnumber writes.

Core entities

  • Link: the short code, the original long URL, when it was made and (optionally) when it expires.
  • User: who created the link. Only needed once we add accounts, which is out of scope today.

API design

One endpoint per functional requirement is enough.

POST/urls

Create a short link. Alias and expiry are optional.

Request body
{
  "long_url": "https://example.com/a/long/page",
  "custom_alias": "my-party",
  "expires_at": "2026-12-31"
}
Response 201 Created
{
  "short_url": "https://sho.rt/x7Kp2Q"
}
GET/{short_code}

Follow a short link. This is what a browser sends when someone clicks it.

Request
GET /x7Kp2Q
Response 302 Found
Location: https://example.com/a/long/page

404 if the code is unknown
410 Gone if it has expired

High-level design

We build it one requirement at a time, simplest version first. I'll assume the usual setup: a few identical app servers that keep no data of their own, behind a load balancer.

1. Creating a short link

The client sends POST /urls. An app server checks the long URL looks valid, makes a new short code (first deep dive), saves the pair in the database and returns the short link.

Table: links
ColumnTypeNote
short_codetextprimary key, e.g. x7Kp2Q
long_urltextwhere the link goes
created_attimestampwhen it was made
expires_attimestamp, optionalempty means never

Because short_code is the primary key, finding a link by its code stays fast even with billions of rows.

Do we need several databases? Say 100M new links a month, which is about 40 per second. At roughly 500 bytes a row, that is 50 GB a month, or about 600 GB a year. One database server handles both easily, so we don't split the data yet.

2. Following a short link

Someone opens sho.rt/x7Kp2Q, so their browser sends GET /x7Kp2Q. The app server looks up the code and replies with status 302 and a Location header holding the long URL. The browser follows it on its own. Unknown codes get 404, expired ones get 410.

Why

Why 302 and not 301? A 301 means "moved permanently", so browsers remember it and skip us on later clicks. That saves traffic but costs control: we can't expire a link, change it, or count clicks. A 302 ("temporarily over there") sends every click back through us. More traffic, which is why the next deep dive is about speed.

Deep dives

How do we keep short codes unique?

We need a short string nobody else already has. Three common approaches:

  1. Use part of the long URL. Take its first few characters. Many URLs start with https://www., so codes clash constantly. Not workable.
  2. Hash the long URL. Run it through a hash function such as SHA-256, write the result in base62, and keep the first 7 characters. The same URL always gives the same code. But two different URLs can occasionally share those 7 characters, so we must check the database and retry with a tweak when that happens.
  3. Count.Pick One counter hands out the next number: 1, 2, 3 and so on. Each new link takes a number and writes it in base62, so 125 becomes 21 (2 × 62 + 1). Two links can never get the same number, so there is nothing to check. An in-memory store like Redis can increase a counter safely for this, even with many app servers asking at once.

I'd pick the counter, because uniqueness comes from the design itself, with no retry logic. Is 7 characters enough? 627 is about 3.5 trillion codes. At 100M links a month we use about 1.2 billion a year, so we would last thousands of years.

The downside: codes come out in order, so neighbouring links are guessable. If that matters, scramble the number with a reversible step before encoding. One counter is no bottleneck at about 40 new numbers a second, and the unique primary key stays as a safety net if it ever repeats a number after a crash.

How do we keep redirects fast?

Every click is a read. If each link is opened about 100 times, our 40 new links a second become about 4,000 redirects a second on average, and several times that at busy moments.

  1. Just the database. A lookup by primary key already takes only a few milliseconds. Fine to start, but every click lands on the database.
  2. Add a cache in front.Pick Keep popular code-to-URL pairs in a cache such as Redis. The app server checks the cache first; on a miss it reads the database and saves the answer for next time. Memory lookups take well under a millisecond, and clicks tend to bunch up on a small set of popular links, so most requests never reach the database.
  3. Cache close to users. Answer redirects from a CDN. Fastest, but harder to expire links or count clicks. A "later" idea.

When a link expires or changes, delete its cache entry too, and never let a cached entry outlive the link's own expiry date.

How do we stay available?

App servers are interchangeable, so losing one is no big deal. The scary failure is the database: if the only copy dies, every redirect fails.

  1. One database plus backups. Cheap, but restoring can take hours, with every link broken meanwhile.
  2. A primary with replicas.Pick Every write goes to the primary and is copied to one or two replicas. If the primary dies, a replica is promoted to take its place. Replicas can also answer redirect lookups.
  3. Copies in several regions. Survives a whole region going offline, at a big cost in complexity. Later, if ever.

Replicas lag a moment behind, so a brand-new link might be missing from one for a fraction of a second. That is the trade we accepted: availability first, perfectly fresh data second.

Final design

Putting the deep dives together gives the complete picture: a counter for unique codes, a cache for fast redirects, and a replica so one database failure doesn't break every link. One change from the first sketch: an API gateway, the single front door that sends each request to the right service, splits the work into a write service and a read service. Clicks vastly outnumber new links, so the read side can be run and scaled on its own.

What you could add next

  • Serve the most popular redirects from a CDN.
  • Hand each write-service instance a block of 1,000 counter values at once, so it rarely asks the counter.
  • Click analytics: record each click in a log that a background job counts later, so redirects stay fast.
  • Split the links table across several databases by short code (called sharding) once it outgrows one machine.

Interview tips

Why 302 instead of 301?
A 302 keeps every click coming through us, so we can expire, change or count links. Browsers cache a 301 and stop asking.
Two people shorten the same URL. Same code?
Not necessarily. A new code each time is simpler; de-duplicate only if asked (hashing gives it for free).
How do custom aliases work?
Check the alias is free (the unique primary key enforces it), and keep aliases in their own space, like sho.rt/c/my-party, so a generated code can never land on one.

Common mistakes

  • Jumping to sharding, queues and microservices before the basic create and redirect flow works.
  • Ignoring the read/write imbalance. Reads outnumber writes by a lot, so the cache is where design effort pays off.
Interview tip

Say the read/write ratio out loud early. It is the one number that justifies the cache, and interviewers listen for it.

Confidence note

The traffic numbers here (100M new links a month, about 100 clicks per link) are assumptions to make the math concrete. Your interviewer may give others. Hashing and counting are both accepted answers; what matters is explaining how you avoid clashes.
