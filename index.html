Design a feature flag service

A team ships a new checkout page, but turns it on for only 10% of users first. If it goes wrong, they switch it off in seconds, with no new release. Every page load asks "is this on for me?", so reads vastly outnumber changes.

Features Qualities Entities API Design Deep dives Tips
Legend 6 terms used below
Feature flag
A named on/off switch stored outside the code. The app asks it whether a feature is on, so the feature can change without a new release.
Hash
A function that turns any text into a number. The same text always gives the same number, and different texts give numbers that look random.
Cache
A fast store, kept in memory, for data we read very often.
TTL
"Time to live": a countdown on a cache entry. When it reaches zero, the entry deletes itself.
API gateway
The single front door that sends each request to the right service.
Replica
A live copy of a database. It takes over if the main one fails.

Functional requirements

  • Create or change a feature flag: on or off, plus a rollout percent (0 to 100).
  • Check whether a flag is on for the current user.

Out of scope: targeting by country or plan, a dashboard, A/B test statistics, login.

Non-functional requirements

  • Fast checks. Every page load asks about several flags, so a slow check slows the whole product.
  • Never break the app. If the flag service is down, the product must keep working.
  • Same answer for the same user. A user must not see the new page, then the old one, on the next refresh.
  • Changes show up within seconds. "Switch it off now" is the whole point.

Core entities

  • Flag: a unique name, an on/off switch and a rollout percent.

API design

PUT/flags/{name}

Creates the flag, or replaces its settings. 201 Created the first time, 200 OK after that, 400 if the percent is outside 0 to 100.

Request body
{ "enabled": true,
  "rollout_percent": 10 }
Response 200 OK
{ "name": "new-checkout",
  "enabled": true,
  "rollout_percent": 10 }
GET/flags/{name}/check

Says whether the flag is on for the caller. The user comes from the auth token. 404 if the flag does not exist.

Request body
(none)
Response 200 OK
{ "name": "new-checkout",
  "on": true }

High-level design

Assume 1 million active users, each page load checking about 10 flags. At peak that is roughly 10,000 checks a second (an assumption), while flags change a few times a day. Servers are identical, keep no data, and sit behind a load balancer.

1. Create or change a flag

The server saves one row. The unique name is the key, so no generated id is needed.

2. Check a flag

The server reads the row. If the flag is off, the answer is no. If it is on, the server takes a hash of flag name plus user id, reduces it to 0-99, and answers yes when that number is below the rollout percent.

Table: flags
ColumnTypeNote
nametextprimary key: the query is "get one flag by name"
enabledbooleanmaster switch
rollout_percentint0 to 100
updated_attimewhen it last changed
Why

Why hash the user instead of rolling a random number? A random roll changes a user's answer on every refresh. A hash always gives the same answer, and raising 10% to 25% keeps the first 10% of users included.

Deep dives

How do we keep checks fast and changes quick?

10,000 identical reads a second of a table that rarely changes is wasted database work.

  1. Read the database every time. Always fresh, but the database does the same read over and over.
  2. Remember flags in each server's memory. Fast, but servers refresh separately, so users could see different answers.
  3. A shared cache.Pick One shared copy, fixed for everyone by one change.

The cache maps flag:{name} to the enabled switch and percent. The check service looks there first and, on a miss, reads the replica and fills the cache. The admin service deletes the entry whenever a flag changes, so the next check loads the new value within a moment. Entries also have a 60-second TTL, a safety net if a delete is missed.

How do we keep the app working if the flag service fails?

A flag check must never be the reason a page does not load.

  1. Wait for the answer. Simple, but an outage becomes the app's outage.
  2. A small client library with fallbacks.Pick It gives up after a short timeout and uses a safe default.

Each app wraps the check in a library with a timeout of about 100 ms. On a timeout or error it uses the last answer it saw, or else a default written in code, usually "off" for new features.

Final design

The dives added a shared cache and a library that falls back to defaults. Checks (about 10,000 a second) and changes (a few a day) are split into two services, so the check side can be scaled on its own. An API gateway routes by path. The primary database has a replica that serves cache misses and takes over on failure. If the cache is lost, checks fall back to the replica, a little slower. A flag a few seconds stale is fine; one stuck wrong is not, so updates delete the cache entry.

What you could add next

  • Targeting rules, such as "only users in India" or "only paid plans".
  • An audit log of who changed which flag and when.
  • Push changes to apps over a persistent connection instead of waiting for the cache.

Interview tips

What if a user logs in on two devices?
Same user id, same hash, same answer on both.
What happens when you raise 10% to 25%?
Users below 10 stay included, and users 10 to 24 are added.
What if the cache holds an old value?
The update deletes the entry, and the 60-second TTL removes anything missed.

Common mistakes

  • Rolling a random number on each check, so users flip between old and new.
  • Letting the app fail when the flag service is slow, instead of using a default.
Interview tip

Say out loud that flags are read thousands of times for every change. It justifies the cache and the split.

Confidence note

The 1 million users and 10 checks per page load are assumptions. Keeping the tiny flag table in each app's memory is also a valid answer.

Design an online poll

A host asks "Pizza or tacos?" and thousands of people tap an answer while the totals move live. It looks like a simple counter, but "one vote each" and a sudden crowd make it a favourite interview question.

Features Qualities Entities API Design Deep dives Tips
Legend 6 terms used below
Primary key
The column (or pair of columns) that must be different in every row. The database refuses a second row with the same key.
Race condition
A bug where two requests at the same instant both pass a check, because neither has finished yet.
Cache
A fast store, kept in memory, for data we read or write very often.
TTL
"Time to live": a countdown on a cache entry. When it reaches zero, the entry deletes itself.
API gateway
The single front door that sends each request to the right service.
Replica
A live copy of a database. It takes over if the main one fails.

Functional requirements

  • Create a poll with a question and 2 to 5 options.
  • Vote on a poll, once per person.
  • See the live total for each option.

Out of scope: changing a vote, anonymous voting, sign-up and login, bot protection.

Non-functional requirements

  • One vote per person. Totals mean nothing if someone can vote twice, even with two taps at the same instant.
  • Never lose a vote. Once we say "recorded", it must survive a crash.
  • Survive a crowd. A shared poll can go viral, so many people vote and watch at once.
  • Slightly stale totals are fine. A total a few seconds behind hurts nobody, but a doubled vote does.

Core entities

  • Poll: a question, its options and a closing time.
  • Vote: which user picked which option in which poll.

API design

POST/polls

Creates a poll. The server picks the id.

Request body
{ "question": "Pizza or tacos?",
  "options": ["Pizza", "Tacos"],
  "closes_at": "2026-11-22T18:00:00Z" }
Response 201 Created
{ "poll_id": 981 }
POST/polls/{poll_id}/votes

Casts the caller's vote. The user comes from the auth token (401 without one). A second vote gets 409 Conflict, a closed poll 410 Gone.

Request body
{ "option_id": 2 }
Response 201 Created
{ "poll_id": 981, "option_id": 2 }
GET/polls/{poll_id}/results

The current total per option. 404 if the poll does not exist.

Request body
(none)
Response 200 OK
{ "total": 1200,
  "options": [ { "option_id": 1, "votes": 700 },
               { "option_id": 2, "votes": 500 } ] }

High-level design

Assume one viral poll gets 1 million votes in 10 minutes, and 100,000 people watch it, refreshing every 2 seconds. Votes are 1,000,000 / 600, about 1,700 a second, which one database handles, so no sharding. Reads are 100,000 / 2, about 50,000 a second: the number to worry about. Servers are identical, keep no data, and sit behind a load balancer.

1. Create a poll

The server inserts a row. The poll id comes from a database sequence.

2. Vote

The server inserts one row per vote. The pair (poll, user) is the primary key, so a second vote by the same person is refused and the server answers 409.

3. See totals

The simplest version counts the votes, grouped by option. Exact, but counting a million rows 50,000 times a second would melt the database.

Tables: polls and votes
ColumnTypeNote
polls.poll_idbigintprimary key, from a sequence
polls.question, options, closes_attext, text, timeread to check the poll is open
votes (poll_id, user_id)bigintprimary key on the pair: one vote each
votes.option_idintwhich option was picked
Why

Why keep every vote, not just a counter per option? A bare counter cannot tell who voted, and cannot be rebuilt if lost. The votes table is the truth; totals are a shortcut.

Deep dives

How do we make sure nobody votes twice?

Two taps from one phone can reach two different servers at the same instant.

  1. Check, then insert. Read "has this user voted?", then insert. Both taps can pass the check, a race condition.
  2. Remember voters on each server. Fast, but another server has never heard of them.
  3. Let the database refuse.Pick The primary key on (poll, user) allows one row.

The database handles the two taps one after the other. The first insert wins and the second fails, which the vote service turns into 409. A retry after a timeout also gets 409, so the app can say "already counted".

How do we show totals to 50,000 readers a second?

Counting a million rows per request is far too slow.

  1. Count on every read. Always exact, but each request scans every vote.
  2. Keep running totals in a cache.Pick Add 1 per accepted vote, read the totals from memory.

The cache holds one entry per poll, poll:{id}:counts, mapping option id to a number. The vote service adds 1 only after the insert succeeded, so a refused duplicate never counts. The results service checks the cache first. On a miss it recounts from the replica and refills the cache. Entries have a one-hour TTL, reset on every vote, so quiet polls drop out and are rebuilt on demand.

Final design

The dives added the key that stops double votes and a cache of totals. Votes (about 1,700 a second) and result reads (about 50,000) are split into two services, so the read side can be scaled on its own. An API gateway routes by path. The primary database has a replica that serves recounts and takes over on failure. If the cache is lost, totals are rebuilt from the votes, a little slower. A crash between the insert and the +1 leaves a total one short until the next rebuild, which is acceptable.

What you could add next

  • Push new totals over a WebSocket instead of refreshing every 2 seconds.
  • Split a very hot poll's total over several cache keys and add them up on read.
  • Rate limit by IP and add bot checks.

Interview tips

What if one user votes from two devices?
Same user id, same primary key, so only the first vote counts.
How would you allow changing a vote?
Update the row, then subtract 1 from the old option and add 1 to the new one.
What if the cache is wrong?
Delete the entry; the next read recounts.

Common mistakes

  • Checking "already voted?" in app code before inserting, which two taps can beat.
  • Counting all vote rows on every results request.
Interview tip

Say who decides "already voted": the database key, not the app code.

Confidence note

The 1 million votes, 100,000 watchers and 2-second refresh are assumptions. Some designs put votes on a queue to absorb bigger spikes; at this size a direct insert is enough.

Design an online presence indicator

A chat app shows a green dot next to friends who are online. It looks simple, but millions of phones must keep saying "I'm here", and a phone that crashes cannot say goodbye.

Features Qualities Entities API Design Deep dives Tips
Legend 8 terms used below
Heartbeat
A tiny "I'm still here" message the app sends on a timer. If the messages stop, the app is gone.
Cursor
A bookmark that says where the last page ended, so the next request continues from there.
WebSocket
A connection that stays open, so the server can send you news without being asked.
Cache
A fast store, kept in memory, for data we read or write very often.
TTL
"Time to live": a countdown on a cache entry. When it reaches zero, the entry deletes itself.
Pub/sub
A message board with channels. Anyone can post to a channel, and everyone listening to it gets the message.
API gateway
The single front door that sends each request to the right service.
Replica
A live copy of a database. It takes over if the main one fails.

Functional requirements

  • While the app is open, keep telling the server "I'm online".
  • See which of your friends are online right now.
  • See friends come online and go offline, live.

Out of scope: "last seen 5 minutes ago", privacy settings, typing indicators, adding friends.

Non-functional requirements

  • Notice a vanished user. A crashed phone sends no goodbye, yet it must turn offline within about a minute.
  • Handle constant writes. Every online user pings all the time, so writes far outnumber reads.
  • Live updates. A friend's dot should change within a few seconds, without refreshing.
  • Slightly stale is fine. A dot that is a few seconds wrong hurts nobody.

Core entities

  • User: an id (from the user service, out of scope).
  • Friendship: a pair of user ids.
  • Presence: whether a user is online, and when we last heard from them.

API design

PUT/me/presence

The heartbeat. The app sends it every 15 seconds (assumed). Safe to repeat. The user comes from the auth token; 401 without one.

Request body
(none)
Response 204 No Content
(empty)
GET/friends/presence?cursor=…

One page of your friends who are online. The cursor marks where the page ended.

Request body
(none)
Response 200 OK
{ "online": [ { "user_id": "u_42" } ],
  "next_cursor": "u_42" }
GET/friends/stream

Upgrades to a WebSocket. The server then pushes each change.

Request body
(none)
Response 101 Switching Protocols, then messages
{ "user_id": "u_42",
  "status": "online" }

High-level design

Assume 1 million people online at once, each pinging every 15 seconds. That is 1,000,000 / 15, about 67,000 writes a second. Keep that number in mind. Servers are identical, keep no data, and sit behind a load balancer.

1. Send a heartbeat

The server saves the current time as the user's last_seen.

2. See who is online

The server reads the user's friend ids, then each friend's last_seen. Seen in the last 45 seconds means online. We cap friends at 500 (assumed) so this stays small.

3. See live changes

The simplest version: the app repeats the friends request every few seconds. It works, but it wastes requests, and the deep dives fix the cost of both write and read sides.

Tables: presence and friendships
ColumnTypeNote
presence.user_idbigintprimary key
presence.last_seentimeupdated on every heartbeat
friendships (user_id, friend_id)bigintprimary key on the pair; serves "my friends"
Why

Why a heartbeat instead of "I closed the app"? A crash, a dead battery or a tunnel sends no goodbye. Silence is the one signal that always works.

Deep dives

How do we notice someone is gone, at 67,000 pings a second?

Offline must show within a minute, and the database cannot take that many writes.

  1. Only trust a "goodbye" message. Cheap, but a crash leaves a user "online" forever.
  2. Save last_seen in the database. Simple, but 67,000 disk writes a second for throwaway data.
  3. A key with a countdown.Pick Each ping resets a cache key that has a TTL.

The key is presence:{user} with a 45-second TTL, which is three missed pings. A missed ping or two is forgiven, so a brief signal drop does not flicker. When the key expires, the user is offline. Presence data is throwaway, so the database never sees it.

How do friends see changes live?

Polling makes every viewer send a request every few seconds, even when nothing changed.

  1. Poll the friends list. Simple, but most replies say "no change".
  2. Tell every friend on every ping. Needs a message per friend per ping, which explodes.
  3. Publish only when the status flips.Pick Friends listen on pub/sub channels.

Each user has a channel. A ping that creates a missing key means "just came online", so the presence service publishes once. The ping that merely resets a key publishes nothing. When a key expires, the cache tells the presence service, which publishes "offline". The friends service holds each viewer's WebSocket, subscribes to the channels of their friends, and forwards what arrives. If pub/sub is down, dots go stale until the app refetches the list.

Final design

The dives added a cache and pub/sub. The write side (presence service) and the read side (friends service) are split because pings vastly outnumber friend lookups. An API gateway routes by path. Friendships sit in a database with a replica that serves reads and takes over on failure. If the cache is lost, everyone looks offline until their next ping, at most 15 seconds.

What you could add next

  • Split the cache by user id once one machine is too small.
  • A "last seen" time kept in the database for offline friends.
  • Skip pushes for users with huge friend lists and fetch on demand.

Interview tips

Why a 45-second TTL for a 15-second ping?
It tolerates two missed pings, so a brief signal drop does not flicker the dot.
Could the heartbeat go over the WebSocket?
Yes, many designs do. A plain request keeps the write path simple and stateless.
What about someone with a million followers?
Do not push to everyone. Show their status only when a profile is opened.

Common mistakes

  • Writing every heartbeat to the main database.
  • Publishing an event on every ping, not only when the status flips.
Interview tip

Say the ping interval and the TTL out loud, and why the TTL is longer.

Confidence note

The 15-second ping, 45-second TTL and 500-friend cap are assumptions. Cache expiry notices can be missed, so some designs add a periodic sweep as a backup.

Design a community feed with upvotes

On a forum site people post, everyone votes, and the best posts rise to the top. The hard part: votes arrive constantly, yet the page must load fast and count each person once.

Features Qualities Entities API Design Deep dives Tips
Legend 8 terms used below
Idempotent
Doing the same request twice has the same result as doing it once.
Cursor
A bookmark that says where the last page ended, so the next request continues from there.
Queue
A line of messages. One service adds to it, another takes from it later, so neither has to wait for the other.
Worker
A background program that takes jobs from a queue and does them.
Cache
A fast store, kept in memory, that holds answers we need often so we skip the slower database.
Sorted set
A cache structure that keeps items ordered by a score, so "give me the top 25" is one quick call.
API gateway
The single front door that sends each request to the right service.
Replica
A live copy of a database. It takes over if the main one fails.

Functional requirements

  • Create a post in a community.
  • Upvote or downvote a post.
  • See a community's feed, with the best posts first.

Out of scope: comments, moderation, search, user profiles.

Non-functional requirements

  • Fast feed. People scroll far more often than they vote.
  • One vote per person. Double counting makes the ranking unfair.
  • Survives a viral post. Thousands of votes can hit one post at once.
  • Counts may lag a little. A score that is a few seconds old is fine.

Core entities

  • Post: id, community, author, title, vote counts, created time.
  • Vote: which user voted on which post, and whether it is +1 or -1.

API design

POST/posts

Creates a post. 422 if the title is empty or over 300 characters (assumed limit). The author comes from the auth token.

Request body
{ "community_id": "c_7",
  "title": "My first post" }
Response 201 Created
{ "post_id": "p_1001" }
PUT/posts/{id}/vote

Sets this user's vote: 1, -1, or 0 to take it back. It is idempotent, so a retry or double click cannot count twice. 404 if the post does not exist.

Request body
{ "value": 1 }
Response 200 OK
{ "post_id": "p_1001",
  "your_vote": 1 }
GET/feed?community=c_7&cursor=…

Returns one page of posts, best first. The cursor is the last post's score and id, not a page number, because scores shift while you scroll.

Request body
(none)
Response 200 OK
{ "posts": [ { "post_id": "p_1001",
    "title": "…", "score": 87 } ],
  "next_cursor": "87_p_1001" }

High-level design

Assume 1 million daily users who vote 10 times each: 10M votes a day, about 115 a second, maybe 600 at peak. One database handles that, so no sharding yet. Identical servers behind a load balancer.

1. Create a post

The server saves a row; its id comes from the database's auto-increment counter.

2. Vote

The server saves one row per (post, user) in a votes table. Making that pair the primary key is what stops a second vote from the same person. The post's up or down count changes too.

3. Show the feed

The simplest version sorts a community's posts by score and returns the first page. A common score uses net votes on a log scale (the 1,000th vote matters less than the 10th) plus a bonus for newer posts.

Tables: posts and votes
ColumnTypeNote
posts.post_idbigintprimary key, auto-increment
community_id, title, created_attext, timeindex (community_id, score) for the feed
up, down, scoreint, floatvote counts and the ranking score
votes (post_id, user_id)bigintprimary key on the pair; value is +1 or -1
Why

Why not just count vote rows for every feed load? The feed is read far more than it is written, so the count should be worked out once at write time, not again on every read.

Deep dives

How do we count votes correctly, even for a viral post?

One post can get hundreds of votes a second, and each user may vote only once.

  1. Add 1 to the post row on every vote. Simple, but a viral post's row becomes a queue of waiters, and a retry counts twice.
  2. Count vote rows on every read. Always right, far too slow.
  3. Votes table as the truth, counts updated in batches.Pick Fast replies and no hot row.

The vote service saves or changes the user's row, works out the change (+1, -1, or +2 for a flipped vote) and adds it to a queue. A worker adds up a batch of changes per post and writes each post once. If the queue is down, the vote is still saved and the worker recounts recent posts from the votes table later.

How do we keep the feed fast?

The feed is the busiest request, and sorting a big table on every load gets slower.

  1. Query the database every time. Every scroll hits the main database.
  2. Cache each finished page. Fast, but every new vote makes pages stale.
  3. A ranked list in the cache.Pick Keep each community's top posts in a sorted set.

The feed service asks the cache for the next 25 ids after the cursor, then reads each post's card from the cache too. The worker, not the feed service, fills it: after each batch it sets the new scores, and once a minute it adds new posts. A new post can take a minute to appear, which is fine. If the cache is lost, the worker rebuilds it from the database.

Final design

The dives added a queue, a score worker and a cache. Posting, voting and reading are separate services because reads vastly outnumber votes, and votes outnumber posts. An API gateway routes by path. The database has a replica that takes over on failure.

What you could add next

  • Split the database by community once one machine is too small.
  • A "new" and "top this week" feed, each with its own ranked list.
  • Spot vote spam before votes reach the queue.

Interview tips

How do you stop one user voting twice?
The votes table has a primary key on (post, user), and the vote API is idempotent.
Why not offset pages like page=3?
Scores change while people scroll, so offsets skip or repeat posts. A cursor does not.
What if the worker falls behind?
Votes are already safe in the table; the scores just lag until it catches up.

Common mistakes

  • Updating one counter row on every vote, so a viral post blocks itself.
  • Counting vote rows on every feed request.
Interview tip

Say out loud which data must be exact (one vote per person) and which may lag (the count).

Confidence note

Traffic, limits and the score formula are assumptions or common choices, not any company's internals.

Design an online code judge

On a coding practice site you paste a solution, press Submit, and a few seconds later it says "Accepted" or "Wrong answer". The site just ran a stranger's program. How do we do that safely, and for thousands of people at once?

Features Qualities Entities API Design Deep dives Tips
Legend 7 terms used below
Verdict
The judge's answer for a submission, such as Accepted, Wrong Answer or Time Limit Exceeded.
Polling
The client asks "is it done yet?" again and again, every second or two, until the answer is ready.
API gateway
The single front door that sends each request to the right service.
Sandbox
A locked room for running code. The program inside can use only what we hand it and cannot touch anything else.
Queue
A line of messages. One service adds to it, another takes from it later, so neither has to wait for the other.
Worker
A background program that takes jobs from a queue and does them one by one.
Replica
A live copy of a database. It takes over if the main one fails.

Functional requirements

  • Submit code, in a chosen language, for a problem.
  • See the verdict for that submission.

Out of scope: contests, leaderboards, writing new problems, the code editor.

Deep dives

How do we spread keys over many machines?

Each key needs a clear owner, and adding a machine should not reshuffle everything.

How do we stay up when a machine dies?

  1. One copy per key. Simple, but data is lost when a node dies.

  3. Three copies with a quorum.Pick Survives one dead node, and never stops.

A key is copied to its owner and the next two nodes on the ring, which are its replicas. A write goes to all three and succeeds once 2 confirm. A read asks 2 and returns the newer version. A quorum of 2 copes with one node down. If two of a key's nodes are down, writes to it fail with 503 rather than risk losing data. Rare stale reads are fine for settings and sessions, not for money.

2. Find jobs that are due

A scheduler process wakes every second and asks for rows where status = 'active' and next_run_at <= now. The index means it reads only due rows. For each, it moves next_run_at to the next cron time, or marks a one-off done.

Why

Why a queue between the scheduler and the workers? The scheduler only decides what is due, which is quick. If it ran tasks itself, one slow task would make every other job late.

Deep dives

How do we never lose a job, and not run it twice?

Servers can crash at any step.

  1. Run the task inside the scheduler. Simplest, but a crash loses the job.
  2. Queue with at-least-once delivery.Pick Never lost, but a message may arrive twice.
  3. Try for exactly-once with distributed transactions. Slow and hard to get right.

With at-least-once delivery, a message stays hidden while a worker holds it. If the worker dies, it reappears after a timeout (5 minutes, assumed). A duplicate is harmless if the task is idempotent. The run_id is the job plus its due time, and a worker skips any run_id already succeeded. Failed runs retry 3 times with growing waits.

How do we start jobs on time when many are due at once?

One scheduler can fail or fall behind.

  1. One scheduler polling the database. Simple, but it stops if it dies.
  2. Several schedulers claiming batches with row locks.Pick No single point of failure, and they split the work.
  3. One in-memory timer per job. Exact, but lost on restart and heavy on memory.

Run two or three schedulers (assumed). Each second, one selects up to 500 due rows with FOR UPDATE SKIP LOCKED, which skips rows another scheduler holds. It enqueues them, moves next_run_at and commits. A crash before the commit releases the locks, so at worst a job is queued twice, which the run_id check handles.

Final design

The dives added run_id checks and several locking schedulers. Services are split by job: the Job API takes writes, the Status API reads from the replica, and the scheduler and workers run in the background so they never slow the API. An API gateway routes by path.

If the primary dies, the replica takes over. If the queue is down, due jobs stay due and run late. Status may be a second stale; claiming jobs always uses the primary.

What you could add next

  • A dead-letter queue for jobs that keep failing, with an alert.
  • Priorities, so urgent jobs skip ahead of bulk ones.
  • Split the jobs table across several databases by job_id when one is not enough.

High-level design

Assume 100,000 IDs a second across the company. The API is identical app servers that keep no user data, behind a load balancer.

1. The obvious start

One database with auto-increment hands out 1, 2, 3. It is unique and sorted, but every ID costs a database round trip, and if that database dies nobody can get an ID.

2. Let each machine make its own

A Snowflake-style ID packs three parts into 64 bits. Two machines can never match, because their machine numbers differ, and one machine never repeats, because its time or its counter always moves on. No talking between machines is needed per ID.

ID layout (64 bits)
PartBitsNote
sign1always 0, so the number stays positive
time41milliseconds since our own epoch; 2^41 ms is about 69 years

sequence12counts 0-4,095 within one millisecond

One machine can make 4,096 IDs per millisecond, about 4 million a second, so three machines already cover 100,000 a second. Time goes in the high bits, so bigger means newer. Machine numbers come from a small registry.

Why

Why not one counter in a database? It is one slow, shared point that everyone waits on. Building the ID from the clock needs no one's permission.

Deep dives

How do we guarantee two machines never make the same ID?

Uniqueness is the whole point, so machine numbers must never be shared by two running servers.

  1. Random UUID. No coordination, but 128 bits and not sorted by time, which makes database indexes slower.
  2. Ticket server (one database counter). Simple, but a bottleneck and a single point of failure.
  3. Snowflake-style with a leased machine number.Pick Small, sorted, and no per-ID coordination.

On start, a server claims a free row in the registry and gets a lease of 30 seconds (assumed). It renews every 10 seconds. If it dies, the lease runs out and the number can be handed to a new server. Without a valid lease it makes no IDs.

How do we handle clock problems?

The design trusts the clock, and clocks sometimes jump back after a time sync.

  1. Ignore it. Fast, but after a jump back the server could repeat an old time and make a duplicate.
  2. Remember the last time used and refuse to go back.Pick Costs a tiny wait or an error, never a duplicate.
  3. Check the time with a central clock service. More exact, but slow and one more thing to fail.

The server keeps the last millisecond it used in memory. If the clock is only a few milliseconds behind, it waits. If further behind, it returns 503 and the load balancer retries another server. If all 4,096 counter values in one millisecond are used, it waits for the next millisecond.

Final design

The dives added the leased machine number and the clock guard. The API gateway splits the two jobs: creating IDs is hot and must scale on its own, while decoding is rare and needs no registry.

The registry has a replica that takes over if the primary dies. If the registry is down, running generators keep going on their current lease; only new servers wait.

What you could add next

  • Hand out IDs in blocks so callers can make a batch locally.
  • Spread generators over several data centres with a data-centre bit.
  • Add a checksum or shuffle so IDs are hard to guess.

Interview tips

What if you need more than 4,096 IDs per millisecond per machine?
Add more machines, or shift a bit or two from the machine part to the sequence.
Why not just use a UUID?
It is twice as big and unsorted, so index inserts are slower.
What happens when the 41 time bits run out?
After about 69 years from our epoch. Choose a recent epoch.

Common mistakes

  • Forgetting that clocks can jump backwards.
  • Giving two running servers the same machine number.

A free weather API lets each app make 100 calls a minute. Call 101 gets a polite "slow down". A rate limiter is that bouncer. The feature is tiny, but it tests counting, sharing one count across servers, and what happens when the counter breaks.

Legend 7 terms used below
Rate limit
The most requests a client may send in a period of time, for example 100 per minute.
429
The HTTP status code "Too Many Requests". It tells the client it was blocked for sending too much, not that the server is broken.
API gateway
The single front door of a system. It receives every request and sends each one to the right service.

A counting method: a bucket holds tokens, each request takes one, and tokens drip back in at a steady speed. No token means no request.

  • Fast. The check runs on every single request, so it may add only a few milliseconds.

High-level design

We build it one requirement at a time. Assume the usual setup: identical servers that keep no data, behind a load balancer.

1. Limiting a client

Every request first meets the limiter. It builds a key from the user id in the auth token plus the endpoint (the IP if there is no token) and asks a shared counter store whether to go ahead. If not, the client gets a 429 with a Retry-After header.

Why

Why block at the front? Turning a request away costs one cheap lookup; letting it in costs the full work of the API. And 429 tells the client the problem is its own speed.

Deep dives

How do we count requests?

Three common ways to decide if one more request fits:

  1. Fixed window. One counter per client per minute, reset when the minute ends. Simple, but 100 requests at 12:00:59 plus 100 at 12:01:00 means 200 in two seconds.
  2. Sliding log. Store the time of every request and count those in the last minute. Exact, but memory-hungry.
  3. Token bucket.Pick A bucket holds up to 100 tokens and refills at 100 per minute. Each request takes one token; empty means 429. Short bursts are fine, the long-run rate stays capped, and we store just two numbers.

No timer is needed: each request works out from last_refill how many tokens dripped in, and adds them.

How do we count correctly across servers?

Two servers may touch the same bucket in the same instant.

  1. Count in each server's memory. Fast, but the limit multiplies by the server count.
  2. Shared Redis, read then write. Two servers both read "1 token left" and both allow.
  3. Shared Redis, one atomic step.Pick A short Lua script inside Redis reads, refills, takes a token and writes back. Redis runs one script at a time, so it is atomic. Cost: one hop of about a millisecond.

Give each bucket key an expiry (TTL) of about a full refill. An idle bucket is full anyway, so deleting it loses nothing.

Final design

The dives added atomic token buckets in Redis. The gateway routes by path to services split by job: the limit service sits on every request, while the rules service handles rare admin changes.

Redis has a replica that takes over if the primary dies, and the rules database has one too. If Redis is still unreachable, the limiter fails open: requests pass and an alert fires.

What you could add next

  • Different limits for free and paid users.
  • Split Redis by client key (sharding) once one primary can't keep up.
  • Let each limiter server allow a few requests from a local count first, to cut Redis calls.

User id from the token if present, else IP (an office can share one IP).
Where should the limiter live?
In the gateway, so every service is covered in one place.
What if Redis goes down?
Fail open and alert; for login attempts you may fail closed.

Common mistakes

  • Counting in each server's memory, so the real limit grows with the server count.
  • Reading the count and writing it back as two steps, which lets a burst slip through.
  • Rejecting with no Retry-After, so clients retry at once.
Interview tip

We build it one requirement at a time, simplest version first. I'll assume the usual setup: a few identical app servers that keep no data of their own, behind a load balancer.

1. Creating a short link

The client sends POST /urls. An app server checks the long URL looks valid, makes a new short code (first deep dive), saves the pair in the database and returns the short link.

Do we need several databases? Say 100M new links a month, which is about 40 per second. At roughly 500 bytes a row, that is 50 GB a month, or about 600 GB a year. One database server handles both easily, so we don't split the data yet.

2. Following a short link

Someone opens sho.rt/x7Kp2Q, so their browser sends GET /x7Kp2Q. The app server looks up the code and replies with status 302 and a Location header holding the long URL. The browser follows it on its own. Unknown codes get 404, expired ones get 410.

Why

Why 302 and not 301? A 301 means "moved permanently", so browsers remember it and skip us on later clicks. That saves traffic but costs control: we can't expire a link, change it, or count clicks. A 302 ("temporarily over there") sends every click back through us. More traffic, which is why the next deep dive is about speed.

Deep dives

How do we keep short codes unique?

We need a short string nobody else already has. Three common approaches:

  1. Use part of the long URL. Take its first few characters. Many URLs start with https://www., so codes clash constantly. Not workable.
  2. Hash the long URL. Run it through a hash function such as SHA-256, write the result in base62, and keep the first 7 characters. The same URL always gives the same code. But two different URLs can occasionally share those 7 characters, so we must check the database and retry with a tweak when that happens.
  3. Count.Pick One counter hands out the next number: 1, 2, 3 and so on. Each new link takes a number and writes it in base62, so 125 becomes 21 (2 × 62 + 1). Two links can never get the same number, so there is nothing to check. An in-memory store like Redis can increase a counter safely for this, even with many app servers asking at once.

I'd pick the counter, because uniqueness comes from the design itself, with no retry logic. Is 7 characters enough? 627 is about 3.5 trillion codes. At 100M links a month we use about 1.2 billion a year, so we would last thousands of years.

The downside: codes come out in order, so neighbouring links are guessable. If that matters, scramble the number with a reversible step before encoding. One counter is no bottleneck at about 40 new numbers a second, and the unique primary key stays as a safety net if it ever repeats a number after a crash.

How do we keep redirects fast?

Every click is a read. If each link is opened about 100 times, our 40 new links a second become about 4,000 redirects a second on average, and several times that at busy moments.

  1. Just the database. A lookup by primary key already takes only a few milliseconds. Fine to start, but every click lands on the database.
  2. Add a cache in front.Pick Keep popular code-to-URL pairs in a cache such as Redis. The app server checks the cache first; on a miss it reads the database and saves the answer for next time. Memory lookups take well under a millisecond, and clicks tend to bunch up on a small set of popular links, so most requests never reach the database.
  3. Cache close to users. Answer redirects from a CDN. Fastest, but harder to expire links or count clicks. A "later" idea.

When a link expires or changes, delete its cache entry too, and never let a cached entry outlive the link's own expiry date.

How do we stay available?

App servers are interchangeable, so losing one is no big deal. The scary failure is the database: if the only copy dies, every redirect fails.

  1. One database plus backups. Cheap, but restoring can take hours, with every link broken meanwhile.
  2. A primary with replicas.Pick Every write goes to the primary and is copied to one or two replicas. If the primary dies, a replica is promoted to take its place. Replicas can also answer redirect lookups.
  3. Copies in several regions. Survives a whole region going offline, at a big cost in complexity. Later, if ever.

Replicas lag a moment behind, so a brand-new link might be missing from one for a fraction of a second. That is the trade we accepted: availability first, perfectly fresh data second.

Final design

Putting the deep dives together gives the complete picture: a counter for unique codes, a cache for fast redirects, and a replica so one database failure doesn't break every link. One change from the first sketch: an API gateway, the single front door that sends each request to the right service, splits the work into a write service and a read service. Clicks vastly outnumber new links, so the read side can be run and scaled on its own.

What you could add next

  • Serve the most popular redirects from a CDN.
  • Hand each write-service instance a block of 1,000 counter values at once, so it rarely asks the counter.
  • Click analytics: record each click in a log that a background job counts later, so redirects stay fast.
  • Split the links table across several databases by short code (called sharding) once it outgrows one machine.

Interview tips

Why 302 instead of 301?
A 302 keeps every click coming through us, so we can expire, change or count links. Browsers cache a 301 and stop asking.
Two people shorten the same URL. Same code?
Not necessarily. A new code each time is simpler; de-duplicate only if asked (hashing gives it for free).
How do custom aliases work?
Check the alias is free (the unique primary key enforces it), and keep aliases in their own space, like sho.rt/c/my-party, so a generated code can never land on one.

Common mistakes

  • Jumping to sharding, queues and microservices before the basic create and redirect flow works.
  • Ignoring the read/write imbalance. Reads outnumber writes by a lot, so the cache is where design effort pays off.
Interview tip

Say the read/write ratio out loud early. It is the one number that justifies the cache, and interviewers listen for it.

Confidence note

The traffic numbers here (100M new links a month, about 100 clicks per link) are assumptions to make the math concrete. Your interviewer may give others. Hashing and counting are both accepted answers; what matters is explaining how you avoid clashes.
